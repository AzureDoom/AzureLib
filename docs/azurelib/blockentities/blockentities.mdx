# How to animate Block Entities

## Creating your custom AzBlockAnimator

For this, you will create a class which extends `AzBlockAnimator`. This class will handle the registration of animation controllers and providing the animation file's location for the animations.

Example:
```java
public class ExampleBEAnimator extends AzBlockAnimator<ExampleBE> {
    private static final ResourceLocation ANIMATIONS = new ResourceLocation(
        YOUR_MOD_ID,
        "animations/item/examplebe.animation.json"
    );

    @Override
    public void registerControllers(AzAnimationControllerContainer<ExampleBE> animationControllerContainer) {
        animationControllerContainer.add(
            AzAnimationController.builder(this, "base_controller")
                .build()
        );
    }

    @Override
    public @Nonnull ResourceLocation getAnimationLocation(ExampleBE animatable) {
        return ANIMATIONS;
    }
}
```

Some highlights of the above example.

- `ANIMATIONS`:
This stores the `ResourceLocation` reference to the animation JSON file. You need to replace `YOUR_MOD_ID` with your mod's ID and ensure the file path matches your JSON animation file.

- `registerControllers()`
Registers the animation controllers that will define the animation behavior and states for the item. You can multiple if needed.

## Creating an Animation Dispatcher

<Callout variant="info">
    You can find more about [AzCommands here](../misc/animating/azcommands_101)
</Callout>

This class isn't required but is highly suggested to help store your animation commands to call in other classes.

Example:
```java
public class ExampleBEDispatcher {
    private static final AzCommand SPINNING_COMMAND = AzCommand.create(
        "base_controller",
        "spinning",
        AzPlayBehaviors.LOOP
    );

    private final BlockEntity blockEntity;

    public ExampleBEDispatcher(BlockEntity blockEntity) {
        this.blockEntity = blockEntity;
    }

    public void spin() {
        SPINNING_COMMAND.sendForBlockEntity(blockEntity);
    }
}
```

## Accessing your Dispatcher to trigger animations

You will now define your ExampleBEDispatcher from above in your `BlockEntity` class.

```java
public class ExampleBE extends BlockEntity {
    // This is your class where you will setup the AzCommands/Animations you wish to play
    public final ExampleBEDispatcher dispatcher;

    public ExampleBE() {
        // Create the instance of the class here to use later.
        this.dispatcher = new ExampleBEDispatcher(this);
    }
}
```

Now you simply call the dispatcher wherever you want to play the animations. A block entity ticks through `tick()`:

```java
    private static final boolean CLIENT = FabricLoader.getInstance().getEnvironmentType() == EnvType.CLIENT;

    @Override
    public void tick() {
        if (CLIENT && this.world != null) {
            // This is where you now trigger an animation to play
            this.dispatcher.spin();
        }
    }
```

<Callout variant="info">
    The check is the Fabric environment, not `world.isMultiplayer` (`isRemote` in other mappings): Beta 1.7.3 single player has no integrated server, so the client's world is not a "remote" world there and that check would never pass. On a multiplayer client the dispatch plays locally; in single player AzureLib applies it straight away.
</Callout>

### The block

Register the block entity class with `AzBlockEntityRegistry` from your OSL `init` entrypoint, which runs on both the client and the server:

```java
public final class YourMod implements ModInitializer {

    @Override
    public void init() {
        AzBlockEntityRegistry.register(ExampleBE.class, "yourmodid_example_be");
    }
}
```

The id is saved with the block entity, so don't change it once worlds exist. Like entity names, it's a plain legacy Beta name rather than a namespaced id, so use `_` instead of `:`. Without this registration Beta throws when it saves the chunk.

If the model replaces the block's look entirely, return `-1` from your block's `getRenderType()` (and `false` from `isSolidRender()`/`isCube()`) so only the block entity renderer draws it. Extending `BlockWithBlockEntity` gives you `createBlockEntity()`:

```java
public class ExampleBlock extends BlockWithBlockEntity {
    public ExampleBlock(int id) {
        super(id, Material.IRON);
    }

    @Override
    protected BlockEntity createBlockEntity() {
        return new ExampleBE();
    }

    @Override
    public int getRenderType() {
        return -1;
    }

    @Override
    public boolean isSolidRender() {
        return false;
    }

    @Override
    public boolean isCube() {
        return false;
    }
}
```

Create the block in your OSL `BlockEvents.REGISTER_BLOCKS` listener. Beta block ids can't be assigned automatically (the save and packet formats only hold 0-255), so pick a free id (vanilla uses up to 96) and register the block under it:

```java
public static void register() {
    EXAMPLE_BLOCK = new ExampleBlock(200);
    BlockRegistry.register(200, NamespacedIdentifiers.from(YOUR_MOD_ID, "example_block"), EXAMPLE_BLOCK);
    EXAMPLE_BLOCK.setKey("yourmodid.example_block"); // name: tile.yourmodid.example_block.name
}
```

The renderer rotates the model by the block's facing. Beta 1.7.3 has no block states, so by default the facing is read from the block metadata (2 north, 3 south, 4 west, 5 east); override `getFacing` in your renderer for other layouts.

### The block's item

To show your animated model in the inventory and in hand, give the block its own plain item that places it, and register an [AzureLib item renderer](../items/items#registering-your-renderer) for that item.

<Callout variant="info">
    Beta only creates block items for the vanilla blocks that exist when its block class first loads, so a mod block has no item of its own anyway. A plain item that places the block also takes the same AzureLib rendering path as any other AzureLib item.
</Callout>

```java
public class ExampleBlockItem extends Item {
    public ExampleBlockItem(int id) {
        super(id);
    }

    @Override
    public boolean useOn(ItemStack stack, PlayerEntity player, World world, int x, int y, int z, int side) {
        // Offset to the clicked face (0 down, 1 up, 2 north, 3 south, 4 west, 5 east), check the spot is free,
        // place YourBlocks.EXAMPLE_BLOCK there and shrink the stack. See StargateItem in the examples.
        ...
    }
}
```

Create the item with `Item.AUTO_ASSIGN_ID` in your `ItemEvents.REGISTER_ITEMS` listener like any other item. Override the block's `getDropItem` to return `Mc.itemId(YourItems.EXAMPLE_BLOCK_ITEM)` so breaking the block gives it back.

## Creating your Renderer

This renderer is responsible for how your custom block entity is displayed in the game.

It connects the block entity with the following:
1. **Geometry file (`geo.json`)**: Defines the 3D model of the block entity.
2. **Texture file (`.png`)**: The visual appearance of the entity (applies over the geometry).
3. **Animator**: Animations for the entity, provided by `ExampleBEAnimator`.

The renderer class must extend `AzBlockEntityRenderer<ExampleBE>` (a Beta 1.7.3 `BlockEntityRenderer`) and provide the required configuration.

<Callout variant="info">
    See [AzRendererConfigs 101](../misc/rendering/azrenderer_config#azblockentityrendererconfig) for all AzBlockEntityRendererConfig#builder options.
</Callout>

Example Renderer
```java
public class ExampleBERenderer extends AzBlockEntityRenderer<ExampleBE> {
    private static final ResourceLocation GEO = new ResourceLocation(
        YOUR_MOD_ID,
        "geo/block/examplebe.geo.json"
    );

    private static final ResourceLocation TEX = new ResourceLocation(
        YOUR_MOD_ID,
        "textures/block/examplebe.png"
    );

    public ExampleBERenderer() {
        super(
            AzBlockEntityRendererConfig.<ExampleBE>builder(GEO, TEX)
                .setAnimatorProvider(ExampleBEAnimator::new).build()
        );
    }
}
```

## Registering your Renderer

Register the renderer on the client with `AzBlockEntityRendererRegistry`, from your OSL `client-init` entrypoint:

```java
public final class YourModClient implements ClientModInitializer {

    @Override
    public void initClient() {
        AzBlockEntityRendererRegistry.register(ExampleBE.class, ExampleBERenderer::new);
    }
}
```

The renderer is created when Beta's block entity render dispatcher is set up (or right away, if it already exists), and it gets the dispatcher assigned the same way vanilla renderers do.
