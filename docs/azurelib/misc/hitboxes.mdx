# Bone Hitboxes

Bone hitboxes let an entity be hit per body part. Each hitbox follows a bone in your model, rotates with it, and stays in sync with whatever animation is playing, because it is read from the same bone matrices the model is drawn with.

## Quick start

Implement `AzHitboxHolder` on your entity and return a static `AzHitboxSet`:

```java
public class ExampleEntity extends MonsterEntity implements AzHitboxHolder {

    private static final AzHitboxSet HITBOXES = AzHitboxSet.builder()
        // Fitted to the head bone's cubes, double damage
        .add("head", h -> h.damageMultiplier(2f).tag("weak_point"))
        .add("body")
        // Second hitbox name on a bone, explicit size in pixels
        .add("tail_tip", "tail4", h -> h.size(4, 4, 10).inflate(1))
        .build();

    public ExampleEntity(World world) {
        super(world);
    }

    @Override
    public AzHitboxSet getHitboxSet() {
        return HITBOXES;
    }
}
```

That is all that is required. The entity must be rendered with an `AzEntityRenderer`. Hold **F3** and press **B** to toggle the hitbox outlines: red is above 1x damage, blue is below 1x, green is 1x, cyan is an interaction hitbox and yellow is an anchor.

Beta has no entity box view of its own, so this toggle is AzureLib's. Beta also opens the debug overlay as soon as F3 is pressed, so press F3 once more afterwards to close it.

## Defining a hitbox

All lengths are Blockbench pixels and offsets use Blockbench's axes, so values can be read straight from the model.

| Method | Effect |
| --- | --- |
| `size(x, y, z)` / `size(s)` | Explicit size. Without it the box fits the cubes owned by the bone (not its children). |
| `offset(x, y, z)` | Moves the box from its default center. |
| `inflate(pixels)` | Grows or shrinks every side. |
| `anchorAtPivot()` | Centers on the bone pivot instead of the center of the bone's cubes. |
| `damageMultiplier(f)` | Used by the default `onHitboxHit`. |
| `tag(String)` | Free-form tags for your own logic. |

A hitbox is disabled while its bone (or a parent hiding its children) is hidden, or scaled to zero.

## Roles

Every hitbox has a role that decides which systems use it:

| Role | Crosshair | Projectiles | `onHitboxHit` | `onHitboxInteract` | Queries |
| --- | --- | --- | --- | --- | --- |
| `COMBAT` (default) | ✓ | ✓ | ✓ | | ✓ |
| `INTERACT` | ✓ | | | ✓ | ✓ |
| `ANCHOR` | | | | | ✓ |

Set it with `.interact()`, `.anchor()` or `.role(AzHitboxRole)`. The crosshair always lands on the nearest pickable box, so a combat hitbox in front of an interaction hitbox blocks the click, the same way a wall would.

### Interaction hitboxes

Right-clicking an `INTERACT` hitbox calls `onHitboxInteract` on both sides, before the entity's own `interact(PlayerEntity)` and before the held item is used on it. Return `true` to consume the click:

```java
.add("saddlebag", "sled", h -> h.interact().size(10, 8, 12).anchorAtPivot().offset(18, -6, 14))
```

```java
@Override
public boolean onHitboxInteract(AzHitboxHit hit, PlayerEntity player) {
    if (hit.name().equals("saddlebag")) {
        if (!Mc.isClientSide(world)) {
            openSaddlebag(player);
        }
        return true;
    }
    return false;
}
```

The client tells the server which hitbox it clicked, and the server checks it against reach, so small or fast-moving interaction hitboxes resolve reliably. This works with `clientOnly()` sets too. Attacking an interaction hitbox deals normal damage with no hitbox attached.

### Anchor hitboxes

An `ANCHOR` hitbox is never hit by anything; it only tracks a bone so your own logic can read its position:

```java
.add("mouth", "lowJaw", h -> h.anchor().size(2))
```

```java
AzOrientedBox mouth = AzHitboxes.getWorldBox(this, "mouth");

if (mouth != null) {
    AzOrientedBox bite = mouth.inflate(0.5);

    for (Entity target : Mc.entities(world)) {
        if (target != this && target instanceof MobEntity && bite.intersects(Mc.boundingBox(target))) {
            target.damage(this, 8);
        }
    }
}
```

Give anchors a non-zero size; a box with no size is treated as empty. On a multiplayer server, anchors follow the pose reported by nearby clients, so they trail the animation by a few ticks and are unavailable when no player is near the mob. Keep a fallback for that case, and time server-side checks slightly after the keyframe they belong to.

## Reacting to hits

`onHitboxHit` runs at the start of `MobEntity#damage(Entity, int)`, on the server (or in the single player world), and returns the damage to apply:

```java
@Override
public int onHitboxHit(AzHitboxHit hit, @Nullable Entity source, int amount) {
    if (hit.hasTag("weak_point")) {
        // React to the weak point: a sound, particles, a stagger animation...
    }
    return Math.round(amount * hit.hitbox().damageMultiplier());
}
```

It runs before vanilla's invulnerability checks, so treat it as a damage modifier. Inside your own `damage` override, `AzHitboxes.getLastHit(this)` returns the same hit for the rest of the tick.

Beta has no damage sources and health is a whole number, so the hook differs from later versions:

- `source` is the player for a melee hit, or the projectile itself for a projectile hit. Beta passes the shooter as the attacker, so the projectile is the more useful of the two; read its owner from it if you need the shooter.
- Projectiles that hit hitboxes are arrows, snowballs, eggs and ghast fireballs.
- The result is an `int`. The default implementation rounds `amount * damageMultiplier()` to the nearest whole point, so a 0.5x hitbox still takes 1 damage from a 1 damage punch.

### After the damage is applied

`onHitboxDamaged` runs on the server once vanilla has accepted the damage, at the end of `LivingEntity#actuallyHurt`. Hits that are blocked by invulnerability frames or `isInvulnerableTo` never reach it, and it runs at most once per hit, so use it for anything that should only change when the entity actually took damage:

```java
@Override
public void onHitboxDamaged(AzHitboxHit hit, DamageSource source, float amount) {
    if (hit.hasTag("armor_plate")) {
        crackPlate(hit.name(), amount);
    }
}
```

`amount` is the damage `onHitboxHit` returned (or, during invulnerability frames, the part above the previous hit), before armor and absorption. The entity's health has already been reduced, so `isDeadOrDying()` tells you whether the hit killed it. [Limb Health](./limb_health) builds on this hook.

<Callout variant="info">
    If your entity overrides `actuallyHurt`, call `super.actuallyHurt` or the hook won't run.
</Callout>

## Querying hitboxes

`AzHitboxes` works on either side:

- `raycast(entity, from, to)` returns the nearest hitbox hit.
- `getIntersecting(entity, box)` returns every hitbox touching a `Box` (for sweeps and area attacks). `Mc.boundingBox(entity)` gives an entity's vanilla box.
- `getWorldBox(entity, name)` and `getActiveHitboxes(entity)` return world-space boxes (for particles, AI targeting).
- `raycast`, `getIntersecting` and `getActiveHitboxes` also take a `Predicate<AzHitbox>`, e.g. `AzHitbox::isPickable` or `h -> h.role() == AzHitboxRole.COMBAT`.
- `hasLivePose(entity)` tells you whether hitboxes are currently active.

## Custom projectiles and hitscan

AzureLib hooks vanilla's projectile collision (`ProjectileUtil.getEntityHitResult`), which arrows, tridents, thrown items and fireballs all use. Projectiles that do their own collision, such as many modded bullets, and hitscan weapons with no projectile entity, never go through it. Against hitbox entities they hit the vanilla box and never trigger `onHitboxHit` or `onHitboxDamaged`.

To give them hitbox support, do two things in your own hit check:

1. Test the shot against the target's hitboxes with `AzHitboxes.raycast`, instead of (or as well as) its bounding box.
2. Right before calling `hurt`, pass the hit to `AzHitboxDamageTracker.recordProjectileHit`. This is how `hurt` finds out which hitbox was hit.

This helper does both, and treats misses the same way vanilla projectiles do:

```java
/**
 * Returns where a shot from {@code from} to {@code to} hits {@code target}, or empty if it misses. If it hits a
 * hitbox, the hit is recorded against {@code direct} for the next {@code hurt} call.
 */
public static Optional<Vec3> clipWithHitboxes(Entity target, Entity direct, Vec3 from, Vec3 to) {
    var boxHit = target.getBoundingBox().clip(from, to);

    if (
        !(target instanceof AzHitboxHolder holder)
            || AzHitboxes.getActiveHitboxes(target, AzHitbox::blocksProjectiles).isEmpty()
    ) {
        return boxHit; // No live hitboxes: use the vanilla box.
    }

    var hit = AzHitboxes.raycast(target, from, to, AzHitbox::blocksProjectiles);
    var keepEntityBox = holder.getHitboxSet().keepEntityBox();

    if (hit.isEmpty()) {
        return keepEntityBox ? boxHit : Optional.empty();
    }

    var location = hit.get().location();

    if (keepEntityBox && boxHit.isPresent() && from.distanceToSqr(boxHit.get()) < from.distanceToSqr(location)) {
        return boxHit; // The vanilla box is closer: a plain body hit.
    }

    if (!target.level().isClientSide()) {
        AzHitboxDamageTracker.recordProjectileHit(direct, hit.get());
    }

    return Optional.of(location);
}
```

Then hurt the target straight away, in the same tick:

```java
if (clipWithHitboxes(target, this, from, to).isPresent()) {
    // thrown(direct, causing): the projectile is the direct entity. Your own damage type works the same way.
    target.hurt(damageSources().thrown(this, getOwner()), damage);
}
```

`direct` must be the entity the damage source names as its direct entity (`DamageSource#getDirectEntity`), because that's what `hurt` looks the hit up by:

- **Projectile entities:** pass the projectile itself, and build the damage source with the projectile as the direct entity, as vanilla does.
- **Hitscan weapons:** there's no projectile, so pass the shooter, and use a damage source whose direct entity is the shooter.

A recorded hit is used once and expires after a tick, so record it right before `hurt` rather than earlier in the projectile's life.

Some more things to check in your own collision code:

- Hitboxes can stick out past the vanilla box. When searching for entities that a shot might hit, inflate the search area by `AzHitboxes.maxOverhang()`, or entities whose hitboxes stick into the shot's path will be skipped.
- Use `AzHitbox::blocksProjectiles` as the filter, so shots pass through `INTERACT` and `ANCHOR` hitboxes like vanilla projectiles do.
- On the server, hitboxes are only live while a nearby client reports the entity's pose (see below). Without one, `clipWithHitboxes` falls back to the vanilla box.

## How syncing works

Animations only run on the client, so the bone positions come from the client.

**Single player.** Beta single player has no separate server: the client runs the world itself. The pose captured while rendering is written straight onto the entity the game logic uses, so melee, interaction, projectiles and your own queries all see the live pose with no syncing and no delay.

**Multiplayer.** The server has no bone positions of its own:

1. **Client:** after the model renders, each hitbox is read from its bone's matrix. Crosshair targeting and client-side projectile checks use these boxes.
2. **Melee:** when you attack, the client tells the server which hitbox the crosshair was on, before the attack itself is sent. The server checks it against reach before using it.
3. **Server:** clients that render the entity report its pose every few ticks. The server listens to the closest one, rejects out-of-range values, and uses the pose for projectiles and reach checks.

AzureLib must be installed on the server for multiplayer hitboxes; the reports travel on AzureLib's own `azurelib:serverbound` channel through OSL Networking.

Entities a nearby player isn't looking at are still posed. Each tick, the client poses any hitbox entity within 64 blocks that it didn't render, by running its animator and computing bone positions without drawing anything, and in multiplayer reports that pose when one is due. Only entities that use an `AzEntityRenderer` get this.

In multiplayer, if no client has reported recently (no player within 64 blocks of the mob), hit detection falls back to the vanilla bounding box.

### Trust

A modified client can move a mob's hitboxes, but only within `maxReach` of the entity and up to `maxHalfExtent` in size. That only changes where projectiles land on that mob. If that is not acceptable for your entity, call `clientOnly()`: melee hitboxes still work, but projectiles use the vanilla box. In single player there is nothing to trust, so `clientOnly()` changes nothing there.

## Set options

| Method | Default | Effect |
| --- | --- | --- |
| `keepEntityBox(true)` | `false` | Keep the vanilla box hittable alongside the hitboxes (as a plain body hit). |
| `clientOnly()` | off | Disable pose reports to the server. |
| `reportInterval(ticks)` | `2` | How often clients report a pose. |
| `poseTimeout(ticks)` | `10` | When a pose is considered stale. |
| `maxReach(blocks)` | `max(4, 3 * max(width, height))` | Furthest a hitbox center may be from the entity. |
| `maxHalfExtent(blocks)` | `4` | Largest accepted hitbox half size. |

## Scaled entities

Hitboxes are read from the same bone matrices the model is drawn with. Any scale applied by the renderer therefore carries over to the hitboxes, including their positions and sizes. Renderer scale is also preserved during render-layer re-renders.

Keep hitbox definitions in unscaled Blockbench pixels. Don't divide or multiply them by your scale.

Minecraft Beta 1.7.3 does not have a scale attribute, so you must synchronize and apply the scale yourself. Three things have to agree: the vanilla bounding box, the rendered model, and the bone hitboxes.

### 1. Sync the scale

Use `DataTracker` to synchronize growth between the server and client. Persist the value to NBT so it survives world reloads.

```java
private static final int GROWTH = 21;

private static final float MAX_GROWTH = 1200f;

private static final float BASE_WIDTH = 0.9f;
private static final float BASE_HEIGHT = 1.9f;

@Override
protected void initDataTracker() {
    super.initDataTracker();
    dataTracker.startTracking(GROWTH, Float.valueOf(0f));
}

public float getGrowthScale() {
    float growth = dataTracker.getFloat(GROWTH);

    return Math.max(
        0.5f,
        Math.min(
            1f,
            0.5f + (growth / MAX_GROWTH) * 0.5f
        )
    );
}

public void setGrowth(float growth) {
    if (!world.isRemote) {
        float clamped = Math.max(
            0f,
            Math.min(MAX_GROWTH, growth)
        );

        dataTracker.set(GROWTH, Float.valueOf(clamped));
        updateScaledDimensions();
    }
}
```

`GROWTH` is a tracked-data index. Choose an unused index that does not conflict with the entity's inherited tracked values.

The server controls growth and synchronizes it through the entity's data tracker. Clients use that same value for rendering and bounding-box calculations.

Save and restore the growth value using the entity's NBT serialization methods. The stored value should be the raw growth amount, not the calculated scale.

```java
// Inside the entity's NBT write method:
tag.putFloat("growth", dataTracker.getFloat(GROWTH));

// Inside the entity's NBT read method:
dataTracker.set(GROWTH, tag.getFloat("growth"));
updateScaledDimensions();
```

Use the NBT method signatures provided by your specific Feather mapping build.

### 2. Scale the entity's bounding box

Beta 1.7.3 uses `setBoundingBoxSpacing(width, height)` instead of `EntityDimensions` and `refreshDimensions()`.

Recalculate the dimensions whenever the synchronized growth value changes.

```java
private float lastAppliedScale = -1f;

private void updateScaledDimensions() {
    float scale = getGrowthScale();

    if (Math.abs(lastAppliedScale - scale) < 0.001f) {
        return;
    }

    lastAppliedScale = scale;

    setBoundingBoxSpacing(
        BASE_WIDTH * scale,
        BASE_HEIGHT * scale
    );
}
```

Call this during initial entity setup, after loading saved growth, and whenever growth changes.

For mappings without a suitable tracked-data update callback, you can check the scale during the entity's regular tick:

```java
@Override
public void tick() {
    super.tick();
    updateScaledDimensions();
}
```

The cached-scale comparison prevents unnecessary bounding-box recalculations when growth has not changed.

This keeps the server and client bounding boxes consistent, including collision handling and client-side entity selection.

If your entity overrides eye height, ensure it follows the scaled dimensions rather than returning an unscaled constant.

### 3. Scale the model and bones

Pass the same scale to AzureLib's renderer configuration:

```java
public ExampleRenderer() {
    super(
        AzEntityRendererConfig.<ExampleEntity>builder(MODEL, TEXTURE)
            .setAnimatorProvider(XenoAnimator::new)
            .setScale(ExampleEntity::getGrowthScale)
            .build()
    );
}
```

AzureLib applies the renderer scale to the model and bone matrices. Since bone hitboxes use those same matrices, their positions and dimensions follow automatically.

Render layers also retain the scale during re-renders.

Do not manually scale hitbox definitions. Doing so would apply scaling twice.

For non-uniform scaling, use the two-function overload:

```java
.setScale(
    ExampleEntity::getHeightScale,
    ExampleEntity::getWidthScale
)
```

**The function overload takes height first, then width.** The float overload uses `setScale(width, height)`.

When applying non-uniform scaling, resize the vanilla bounding box with the corresponding width and height functions.

You can also adjust the renderer's shadow radius to follow the entity's scale.

### Important notes

- Keep all hitbox definitions in their original Blockbench pixel dimensions.
- Growth must be synchronized between server and client.
- Update the vanilla bounding box independently of the renderer.
- Do not repeatedly multiply the existing entity width or height. Always calculate from the unscaled base dimensions.
- Scale-sensitive values such as eye height and shadow radius may need separate adjustments.

## Large entities

Beta's server rejects an attack or interaction when the target's position is 6 or more blocks away. For hitbox holders, AzureLib measures that distance to the nearest pickable hitbox instead, so a long tail can be hit from where it reaches.

If hitboxes stick far outside the vanilla box (long tails or necks), the game can also skip drawing the entity while part of it is on screen, which stops the hitboxes updating. Override Beta's render distance check (MCP `Entity#isInRangeToRenderDist`) and size it from the culling box:

```java
public ExampleEntity(World world) {
    super(world);
    this.ignoreCameraFrustum = true;
}

@Override
public boolean isWithinRenderDistance(double distanceSq) {
    Box box = AzHitboxes.getCullingBox(this, Mc.boundingBox(this));
    double size = (box.maxX - box.minX + box.maxY - box.minY + box.maxZ - box.minZ) / 3.0;
    double range = size * 64.0 * this.viewDistanceScaling;
    return distanceSq < range * range;
}
```
