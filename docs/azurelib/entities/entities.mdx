# How to animate Entities

## Creating your custom AzEntityAnimator

For this, you will create a class which extends `AzEntityAnimator`. This class will handle the registration of animation controllers and providing the animation file's location for the animations.

Example:
```java
public class ExampleEntityAnimator extends AzEntityAnimator<ExampleEntity> {
    private static final ResourceLocation ANIMATIONS = new ResourceLocation(
        YOUR_MOD_ID,
        "animations/entity/example_entity.animation.json"
    );

    @Override
    public void registerControllers(AzAnimationControllerContainer<ExampleEntity> animationControllerContainer) {
        animationControllerContainer.add(
            AzAnimationController.builder(this, "base_controller")
                .build()
        );
    }

    @Override
    public @Nonnull ResourceLocation getAnimationLocation(ExampleEntity animatable) {
        return ANIMATIONS;
    }
}
```

Some highlights of the above example.

- `ANIMATIONS`:
This stores the `ResourceLocation` reference to the animation JSON file. You need to replace `YOUR_MOD_ID` with your mod's ID and ensure the file path matches your JSON animation file.

- `registerControllers()`
Registers the animation controllers that will define the animation behavior and states for the item. You can multiple if needed.

## Creating an Animation Dispatcher

<Callout variant="info">
    You can find more about [AzCommands here](../misc/animating/azcommands_101)
</Callout>

This class isn't required but is highly suggested to help store your animation commands to call in other classes.

Example:
```java
public class ExampleEntityDispatcher {
    private static final AzCommand IDLE_COMMAND = AzCommand.create(
        "base_controller",
        "idle",
        AzPlayBehaviors.LOOP
    );

    private static final AzCommand WALK_COMMAND = AzCommand.create(
        "base_controller",
        "walking",
        AzPlayBehaviors.LOOP
    );

    private static final AzCommand RUN_COMMAND = AzCommand.create(
        "base_controller",
        "running",
        AzPlayBehaviors.LOOP
    );

    private static final AzCommand DEATH_COMMAND = AzCommand.create(
        "base_controller",
        "death",
        AzPlayBehaviors.HOLD_ON_LAST_FRAME
    );

    private final ExampleEntity example_entity;

    public ExampleEntityDispatcher(ExampleEntity animatable) {
        this.example_entity = animatable;
    }

    public void idle() {
        IDLE_COMMAND.sendForEntity(example_entity);
    }

    public void walk() {
        WALK_COMMAND.sendForEntity(example_entity);
    }

    public void run() {
        RUN_COMMAND.sendForEntity(example_entity);
    }

    public void death() {
        DEATH_COMMAND.sendForEntity(example_entity);
    }
}
```

## Accessing your Dispatcher to trigger animations

You will now define your ExampleEntityDispatcher from above in your Entities class. It is also recommended to register the MoveAnalysis utility class if you'd like to do movement based animations.

```java
public class ExampleEntity extends MobEntity {
    // This is your class where you will setup the AzCommands/Animations you wish to play
    public final ExampleEntityDispatcher dispatcher;

    public final MoveAnalysis moveAnalysis;

    public ExampleEntity(World world) {
        super(world);
        this.setSize(0.6F, 1.8F);
        // Create the instance of the class here to use later.
        this.dispatcher = new ExampleEntityDispatcher(this);
        this.moveAnalysis = new MoveAnalysis(this);
    }
}
```

Beta 1.7.3 entities need a constructor taking only a `World`; that's what Beta 1.7.3 calls when it loads the entity from disk or spawns it on a multiplayer client. Any Beta 1.7.3 mob class works as the base class (`MobEntity`, `MonsterEntity`, `AnimalEntity`, ...); for multiplayer, see the tracking note under [Registering your Entity](#registering-your-entity).

Now you simply call the dispatcher wherever you want to play the animations.

<Callout variant="warning">
    Beta 1.7.3 mobs have no synced "aggressive" or "attacking" state, and their target only exists where the AI runs. If a client-side animation choice depends on server state (attacking, charging, ...), sync it through the entity's `SyncedData`, as `isAggressive()` does below. Beta 1.7.3's synced data supports bytes, shorts, ints, strings and item stacks; IDs go up to 31 and are shared with vanilla: `Entity` uses 0 and vanilla mobs use 16–18, so 19 and up are safe.
</Callout>

<Callout variant="info">
    Beta 1.7.3 has no goal-based AI. Mobs extending Beta 1.7.3's creature classes wander and pick targets on their own, and get a `targetInSight(Entity, float)` callback while their target is in sight; that's where you would trigger an attack animation.
</Callout>

Example of playing a death animation, movement animations and an idle animation.

<Callout variant="warning">
    Don't pick render-driven animations in `tick()` with a `world.isMultiplayer`-style check (`isRemote` in other mappings). Beta 1.7.3 single player has no integrated server: the client runs the world itself, so there is no client-side world to check for and that branch never runs. Instead, choose looping state animations from the renderer (which only exists on the client), as below, and keep `tick()` for server logic.
</Callout>

```java
    /** SyncedData slot for the synced "has an attack target" flag. */
    private static final int AGGRESSIVE = 20;

    @Override
    protected void registerSyncedData() {
        super.registerSyncedData();
        this.syncedData.register(AGGRESSIVE, (byte) 0);
    }

    public boolean isAggressive() {
        return this.syncedData.getByte(AGGRESSIVE) != 0;
    }

    @Override
    public void tick() {
        super.tick();
        moveAnalysis.update();

        if (!Mc.isClientSide(this.world)) {
            // Server (or the single player world): keep the synced flag up to date from your AI state.
            this.syncedData.update(AGGRESSIVE, (byte) (this.walkTarget != null ? 1 : 0));
        }
    }

    /** Called every frame by the renderer, see "Creating your Renderer" below. */
    public void updateAnimations() {
        boolean isMovingOnGround = moveAnalysis.isMovingHorizontally() && Mc.onGround(this);
        if (Mc.health(this) <= 0) { // if dead, play death animation
            dispatcher.death();
        } else if (isMovingOnGround) {
            if (this.isAggressive()) { // if moving and aggressive, play running
                dispatcher.run();
            } else { // if moving but not aggressive play walk
                dispatcher.walk();
            }
        } else { // Play the default idle animation
            dispatcher.idle();
        }
    }
```

One-off animations caused by game logic (an attack, an ability) are best sent from the server side when they happen, for example `dispatcher.melee()` from your attack code. `sendForEntity` sends them to every player that can see the entity, and plays them directly in single player.

<Callout variant="info">
    Beta 1.7.3 removes a dead mob after 20 ticks (one second), so death animations longer than that get cut off.
</Callout>

## Creating your Renderer

This renderer is responsible for how your custom entity is displayed in the game.

It connects the entity with the following:
1. **Geometry file (`geo.json`)**: Defines the 3D model of the entity.
2. **Texture file (`.png`)**: The visual appearance of the entity (applies over the geometry).
3. **Animator**: Animations for the entity, provided by `ExampleEntityAnimator`.

The renderer class must extend `AzEntityRenderer<ExampleEntity>` (a Beta 1.7.3 `EntityRenderer`) and provide the required configuration. Beta 1.7.3 renderers are plain instances; AzureLib assigns the render dispatcher when it installs the renderer (see [Registering your Renderer](#registering-your-renderer)).

<Callout variant="info">
    See [AzRendererConfigs 101](../misc/rendering/azrenderer_config#azentityrendererconfig) for all AzEntityRendererConfig#builder options.
</Callout>

Example Renderer
```java
public class ExampleEntityRenderer extends AzEntityRenderer<ExampleEntity> {
    private static final ResourceLocation GEO = new ResourceLocation(
        YOUR_MOD_ID,
        "geo/entity/example_entity.geo.json"
    );

    private static final ResourceLocation TEX = new ResourceLocation(
        YOUR_MOD_ID,
        "textures/entity/example_entity.png"
    );

    public ExampleEntityRenderer() {
        super(
            AzEntityRendererConfig.<ExampleEntity>builder(GEO, TEX)
                .setAnimatorProvider(ExampleEntityAnimator::new)
                // Pick the looping state animation every frame on the client.
                .setPrerenderEntry(context -> {
                    context.animatable().updateAnimations();
                    return context;
                })
                .build()
        );
    }
}
```

## Registering your Entity

Register the entity class with `AzEntityRegistry` from your OSL `init` entrypoint, which runs on both the client and the server:

```java
public final class YourMod implements ModInitializer {

    @Override
    public void init() {
        AzEntityRegistry.register(ExampleEntity.class, "yourmodid_example_entity", 120);
    }
}
```

<Callout variant="info">
    - The **name** is saved with the entity, so don't change it once worlds exist. It's a legacy Beta entity name that OSL converts to a namespaced id itself, so use letters, digits, `_`, `.`, `-` or `/` only, never `:` (`yourmodid_example_entity`, not `yourmodid:example_entity`).
    - The **numeric id** is what multiplayer spawn packets carry. Beta sends it as a signed byte, so mobs need an id from 1 to 127 to appear on multiplayer clients (AzureLib logs a warning above that). Vanilla uses ids up to about 97; AzureLib throws if the id or name is already taken.
    - Beta's server only sends entities it recognises to clients: mobs and animals (anything extending the vanilla mob base classes) work, other custom entities need their own tracker mixin. A class that extends `MobEntity` directly isn't tracked either, so extend `MonsterEntity` or `AnimalEntity` if it should appear in multiplayer.
</Callout>

## Registering your Renderer

Register the renderer on the client with `AzEntityRendererRegistry`, from your OSL `client-init` entrypoint:

```java
public final class YourModClient implements ClientModInitializer {

    @Override
    public void initClient() {
        AzEntityRendererRegistry.register(ExampleEntity.class, ExampleEntityRenderer::new);
    }
}
```

The renderer is created when Beta's entity render dispatcher is set up (or right away, if it already exists), and it gets the dispatcher assigned the same way vanilla renderers do. You can also give a vanilla entity an AzureLib renderer the same way, for example `AzEntityRendererRegistry.register(CreeperEntity.class, ExampleCreeperRenderer::new)`; it replaces the vanilla renderer for that class.
