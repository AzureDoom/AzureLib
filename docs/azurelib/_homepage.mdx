## Developers

<Callout variant="info">
    These docs are for the **Beta 1.7.3** version of AzureLib, which runs on **Babric** (Fabric Loader for Beta) and requires **StationAPI**. It needs Java 17, Fabric Loom with the babric extension and the BINY mappings, so the code on these pages uses BINY class names (`LivingEntity`, `PlayerEntity`, `BlockEntity`, `World`...).

    You can find working examples [here](https://github.com/AzureDoom/Azurelib-Rewrite-Examples/tree/b1.7.3).
</Callout>

<Callout variant="warning">
    **StationAPI is required.** AzureLib uses it for item NBT (the identity that lets animations target a single item stack, synced to clients), for networking, and for its asset loading and rendering hooks. Install StationAPI alongside AzureLib on both the client and the server, and depend on it in your mod.
</Callout>

To add AzureLib to your project as a dependency you need to add the following to your `build.gradle`:

<CodeTabs>

```markdown !!tabs build.gradle
repositories {
	maven {
		name = "AzureDoom Mods"
		url = "https://maven.azuredoom.com/mods"
	}
	// StationAPI and its dependencies
	maven { url = "https://maven.glass-launcher.net/snapshots/" }
	maven { url = "https://maven.glass-launcher.net/releases/" }
	maven { url = "https://maven.glass-launcher.net/babric" }
}
```

</CodeTabs>

The Gradle property `MODVERSION` should be the AzureLib version, for example `1.0.0`. Versions can be found on [CurseForge](https://www.curseforge.com/) and [Modrinth](https://modrinth.com/mod/azurelib). `STATIONAPI_VERSION` is the StationAPI version you build against, for example `2.0.0-alpha.6.4`.

<CodeTabs>

```markdown !!tabs Beta 1.7.3 (Babric + StationAPI)
dependencies {
	minecraft "com.mojang:minecraft:b1.7.3"
	mappings "net.glasslauncher:biny:${yarn_mappings}:v2"
	modImplementation "net.fabricmc:fabric-loader:${loader_version}"

	// Required by AzureLib
	modImplementation "net.modificationstation:StationAPI:STATIONAPI_VERSION"

	modImplementation "mod.azure.azurelib:azurelib-stationapi-b1.7.3:MODVERSION"
}
```

</CodeTabs>

Then declare both dependencies in your `fabric.mod.json`, so Fabric Loader refuses to start without them:

```json
"depends": {
	"minecraft": "1.0.0-beta.7.3",
	"stationapi": "*",
	"azurelib": "*"
}
```

AzureLib registers its own mixins and initializes itself through Fabric entrypoints, so there's nothing else to set up.

### Where to register things

Beta has no registry events of its own; registration happens through StationAPI's event bus. Add entrypoints for it to your `fabric.mod.json`:

```json
"entrypoints": {
	"stationapi:event_bus": [
		"yourmod.registry.YourModEvents"
	],
	"stationapi:event_bus_client": [
		"yourmod.client.YourModClientEvents"
	]
}
```

Each class is a plain class with static `@EventListener` methods (StationAPI also needs a lookup registered once per class):

```java
public final class YourModEvents {
    static {
        EntrypointManager.registerLookup(MethodHandles.lookup());
    }

    public static final Namespace NAMESPACE = Namespace.of(YOUR_MOD_ID);

    @EventListener
    private static void registerItems(ItemRegistryEvent event) {
        // create your items here, then register AzureLib item identities (see the Items pages)
    }
}
```

The pages for entities, items, armor and block entities show which StationAPI event each AzureLib registration goes in.

### Things that differ from other versions

<Callout variant="info">
    - **`ResourceLocation`**: Beta has none, so AzureLib provides `mod.azure.azurelib.util.ResourceLocation`. `new ResourceLocation("yourmodid", "geo/entity/example.geo.json")` resolves to `assets/yourmodid/geo/entity/example.geo.json` in your jar, exactly like on other versions. The `minecraft` namespace points at Beta's own assets at the jar root (`minecraft:mob/zombie.png` is `/mob/zombie.png`).
    - **Assets**: AzureLib reads `geo/`, `animations/` and textures straight from every loaded mod, so the asset layout is the same as on other versions. Models and animations load the first time they are used; call `AzureLibCache.reload()` to reload them while testing.
    - **Vanilla fields**: Beta's mapped field and method names can change between BINY builds. AzureLib reads vanilla state through two small bridge classes, `mod.azure.azurelib.platform.mc.Mc` (common) and `McClient` (client), which you can use too, for example `Mc.isClientSide(world)`, `Mc.heldItem(entity)` or `Mc.armor(entity, slot)`.
    - **Single player**: Beta has no integrated server; the client runs the world itself. AzureLib handles that for you, so server-side dispatches (`AzCommand#sendForEntity` and friends) behave the same in single player and multiplayer.
</Callout>
