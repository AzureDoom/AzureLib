# How to animate Items

## Creating your custom AzItemAnimator

For this, you will create a class which extends `AzItemAnimator`. This class will handle the registration of animation controllers and providing the animation file's location for the animations.

Example:
```java
public class ExampleItemAnimator extends AzItemAnimator {
    private static final ResourceLocation ANIMATIONS = new ResourceLocation(
        YOUR_MOD_ID,
        "animations/item/exampleitem.animation.json"
    );

    @Override
    public void registerControllers(AzAnimationControllerContainer<ItemStack> animationControllerContainer) {
        animationControllerContainer.add(
            AzAnimationController.builder(this, "base_controller")
                .build()
        );
    }

    @Override
    public @Nonnull ResourceLocation getAnimationLocation(ItemStack animatable) {
        return ANIMATIONS;
    }
}
```

Some highlights of the above example.

- `ANIMATIONS`:
This stores the `ResourceLocation` reference to the animation JSON file. You need to replace `YOUR_MOD_ID` with your mod's ID and ensure the file path matches your JSON animation file.

- `registerControllers()`
Registers the animation controllers that will define the animation behavior and states for the item. You can multiple if needed.

## Creating an Animation Dispatcher

<Callout variant="info">
    You can find more about [AzCommands here](../misc/animating/azcommands_101)
</Callout>

This class isn't required but is highly suggested to help store your animation commands to call in other classes.

Example:
```java
public class ExampleItemDispatcher {
    private static final AzCommand FIRING_COMMAND = AzCommand.create("base_controller", "firing", AzPlayBehaviors.PLAY_ONCE);

    public void firing(Entity entity, ItemStack itemStack) {
        FIRING_COMMAND.sendForItem(entity, itemStack);
    }
}
```

## Accessing your Dispatcher to trigger animations

You will now define your ExampleItemDispatcher from above in your Item class.

```java
public class ExampleItem extends Item {
    // This is your class where you will setup the AzCommands/Animations you wish to play
    public final ExampleItemDispatcher dispatcher;

    public ExampleItem(Identifier identifier) {
        // StationAPI hands out the numeric item ID
        super(ItemTemplate.getNextId());
        ItemTemplate.onConstructor(this, identifier);
        this.setMaxCount(1);
        // Create the instance of the class here to use later.
        this.dispatcher = new ExampleItemDispatcher();
    }
}
```

Create it in StationAPI's `ItemRegistryEvent` with an identifier from your namespace, for example `new ExampleItem(NAMESPACE.id("example_item"))`.

Now to use the dispatcher, you would simply call it in any method where you want it trigger for, like if I want the firing to happing on use, I would do it like so:
```java
    @Override
    public ItemStack use(ItemStack stack, World world, PlayerEntity player) {
        if (!Mc.isClientSide(world)) {
            // This is where you now trigger an animation to play
            dispatcher.firing(player, stack);
        }
        return stack;
    }
```

<Callout variant="info">
    Beta 1.7.3 has no "hold to use" items: `use` runs once per right click, and holding the button repeats it every few ticks. Add your own cooldown if an action shouldn't repeat that fast. `!Mc.isClientSide(world)` is true on the server and in single player, which is where dispatches should come from.
</Callout>

## Creating your Renderer

This renderer is responsible for how your custom item is displayed in the game.

It connects the item with the following:
1. **Geometry file (`geo.json`)**: Defines the 3D model of the item.
2. **Texture file (`.png`)**: The visual appearance of the item (applies over the geometry).
3. **Animator**: Animations for the item, provided by `ExampleItemAnimator`.

<Callout variant="info">
    See [AzRendererConfigs 101](../misc/rendering/azrenderer_config#azitemrendererconfig) for all AzItemRendererConfig#builder options.
</Callout>
<Callout variant="warning">
    There is currently a bug in the plugin which exports the displays with an offset applied, please use useNewOffset(true) in your AzItemRendererConfig builder to fix this.
</Callout>

```java
public class ExampleItemRenderer extends AzItemRenderer {
    private static final ResourceLocation GEO = new ResourceLocation(
        YOUR_MOD_ID,
        "geo/item/exampleitem.geo.json"
    );

    private static final ResourceLocation TEX = new ResourceLocation(
        YOUR_MOD_ID,
        "textures/item/exampleitem.png"
    );

    public ExampleItemRenderer() {
        super(
            AzItemRendererConfig.builder(GEO, TEX)
                .setAnimatorProvider(ExampleItemAnimator::new).build()
        );
    }
}
```


## Different animations in first person and third person

By default an item stack has one animator, so whatever plays in first person also plays in third person. If you want the two views to play different animations at the same time (for example an aimed fire in first person while other players see a hip fire), opt in with `useSeparateFirstPersonAnimator()`. The first-person hand contexts then get their own animator with their own controllers, bone state and timer; third person, GUI, ground, item frames and every other context keep using the default animator.

```java
public ExampleItemRenderer() {
    super(
        AzItemRendererConfig.builder(GEO, TEX)
            .setAnimatorProvider(ExampleItemAnimator::new)
            .useSeparateFirstPersonAnimator()
            .build()
    );
}
```

Both animators are built from the same `AzItemAnimator`, so they share controller names and the same animation file. Target one view when you dispatch:

```java
public class ExampleItemDispatcher {
    private static final AzCommand AIM_FIRING = AzCommand.create("base_controller", "aimfiring", AzPlayBehaviors.PLAY_ONCE);
    private static final AzCommand FIRING = AzCommand.create("base_controller", "firing", AzPlayBehaviors.PLAY_ONCE);

    public void firing(Entity entity, ItemStack itemStack) {
        AIM_FIRING.sendForItemFirstPerson(entity, itemStack);
        FIRING.sendForItemThirdPerson(entity, itemStack);
    }
}
```

`sendForItem(entity, stack)` without a view still plays on both animators, and `sendForItem(entity, stack, AzItemAnimatorView)` lets you pick the view from a variable. For anything other than a plain first/third split, `setAnimatorViewProvider(context -> ...)` maps each `AzItemDisplayContext` to a view yourself.

## Registering your Renderer

Call `AzItemRendererRegistry#register()` on the client. A good place is StationAPI's `TextureRegisterEvent` in your `stationapi:event_bus_client` entrypoint, because your items exist by then. AzureLib then draws the item everywhere: in the GUI, in first and third person, and on the ground.

Beta 1.7.3 items have no registry names, so AzureLib can't find the Blockbench-exported item model (with its `display` transforms) by name the way other versions do. Pass its location when you register:

```java
@EventListener
private static void registerTextures(TextureRegisterEvent event) {
    AzItemRendererRegistry.register(
        YourItemRegistry.YOUR_ITEM,
        new ResourceLocation(YOUR_MOD_ID, "models/item/exampleitem.json"),
        ExampleItemRenderer::new
    );
}
```

Only the `display` block of that file is used; the parent is ignored. `AzItemRendererRegistry.register(ExampleItemRenderer::new, YourItemRegistry.YOUR_ITEM)` also works if you don't need display transforms.

```json
// assets/yourmodid/models/item/exampleitem.json
{
  "parent": "builtin/entity",
  "display": {
    // display transforms exported from Blockbench
  }
}
```

<Callout variant="info">
    Beta 1.7.3 only distinguishes four contexts, which AzureLib maps to `GUI`, `GROUND`, `FIRST_PERSON_RIGHT_HAND` and `THIRD_PERSON_RIGHT_HAND`. If an item sits wrong in one of them, override `AzItemRenderer#applyBaseTransform`.
</Callout>

<Callout variant="info">
    AzureLib draws through StationAPI's item renderer (Arsenic). Arsenic only hands an item back to vanilla-style rendering, where AzureLib takes over, when the item has **no** StationAPI JSON item model. So don't give AzureLib-rendered items a model under `assets/<modid>/stationapi/models/`. The same applies to block items: StationAPI's automatic block items always get the block's model, so place an AzureLib-rendered block with a plain item of your own (see [Block Entities](../blockentities/blockentities)).
</Callout>

To keep a flat sprite in one context while AzureLib draws the model everywhere else, use `useVanillaRenderingIn` on the config builder, for example `.useVanillaRenderingIn(AzItemDisplayContext.GUI)` together with an item icon set through StationAPI's `item.setTexture(...)`.

## Registering your Item for proper animation triggering

To ensure trigger animations work properly, you will need to also call `AzIdentityRegistry#register()` on both the client and the server, after your items are created. The end of your `ItemRegistryEvent` listener (in the common `stationapi:event_bus` entrypoint) is the natural place:

```java
@EventListener
private static void registerItems(ItemRegistryEvent event) {
    YourItemRegistry.register();
    AzIdentityRegistry.register(YourItemRegistry.YOUR_ITEM, ...);
}
```

Stacks of registered items get a UUID in StationAPI's per-stack NBT when they are created. StationAPI saves it and syncs it to clients, which is how a dispatch from the server finds the same stack on every client. Vanilla items can be registered too, for example `Item.DIAMOND_SWORD`.
